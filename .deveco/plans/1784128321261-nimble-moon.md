## Goal

修复 `hvigor ERROR: Failed :entry:default@CompileArkTS` 构建失败。**仅修改导致编译 ERROR 的代码，WARN 级别不做处理。**

## 问题诊断

### 已知信息

构建输出中**只有 WARN，没有显示具体 ERROR 详情**（可能被截断）。170 条 WARN 全部来自 `relationalStore` 异常处理和 `pushUrl` 弃用 — 这些都是 **WARN 级别，不会导致构建失败**。

### 根因推测

真正的 `CompileArkTS` ERROR 信息在提供给我们的输出中被截断。可能的 ERROR 来源：

| 嫌疑 | 位置 | 可能性 |
|---|---|---|
| 元组字面量无类型上下文 | `[BackgroundConfig.ets:14-49](entry/src/main/ets/model/BackgroundConfig.ets)` 中 `[string, number]` 嵌套数组 | 中 |
| `@BuilderParam` 缺失 | `[PageBackground.ets](entry/src/main/ets/components/PageBackground.ets)` 未按计划使用 `@BuilderParam`，但作为 `Stack` 子组件 | 低 |
| 其他未见的 ERROR | 需通过 `arkts_check` 诊断 | 高 |

### 诊断策略

- **不猜测 ERROR** — 直接用 `arkts_check` 工具对全部 `.ets` 文件做严格检查
- 只修复检查输出的 ERROR（通常包含 `arkts-` 规则标签或 `error` 关键词）
- WARN 一律跳过

## Design

### 诊断顺序

```
Step 1: arkts_check → 获取 ERROR 列表
Step 2: 根据 ERROR 定位修复
Step 3: 重新构建 → 验证通过
```

### 预期可能的修复（根据 arkts_check 结果）

由于我们看不到实际 ERROR，以下是 `arkts_check` 可能报告的常见问题及对应修复方案：

#### 场景 A：元组类型问题（`arkts-no-untyped-obj-literals`）

如果在 `BackgroundConfig.ets` 的 `GRADIENT_PRESETS` 中，嵌套的 `[['#FF9A9E', 0.0], ...]` 被报告为无类型上下文：

**修复**: 将 `colors` 改为显式赋给一个类型化变量：

```typescript
// Before
colors: [['#FF9A9E', 0.0], ['#FAD0C4', 1.0]]

// After
const sunriseColors: Array<[string, number]> = [['#FF9A9E', 0.0], ['#FAD0C4', 1.0]];
// 在对象中引用: colors: sunriseColors
```

#### 场景 B：缺失 `import` 或 `export`

如果某个类型/函数在源文件声明但未 `export`，或在消费文件未 `import`：

**修复**: 补充缺失的 `export`/`import`。

#### 场景 C：类型不匹配

**修复**: 根据 `arkts_check` 具体报告的类型进行修正。

#### 场景 D：其他 ArkTS 语法违规

根据 `arkts_check` 的具体 `arkts-*` 规则标签，按照 ArkTS 语法规范修复。

## Execution Sequence

### Step 1: 诊断



## Risks And Compatibility

| 风险 | 缓解 |
|---|---|
| 真实 ERROR 不在我们分析的文件中 | `arkts_check` 扫描全部 `.ets` 文件，全覆盖 |
| ERROR 是资源引用问题（非代码） | 如 `arkts_check` 零错误但构建仍失败，则需检查 `main_pages.json`、图片资源、`string.json` 等配置 |
